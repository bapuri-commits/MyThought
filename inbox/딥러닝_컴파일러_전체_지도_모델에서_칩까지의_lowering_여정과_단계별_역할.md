# 딥러닝 컴파일러 전체 지도 — 모델에서 칩까지의 lowering 여정과 단계별 역할

## 발단 · 생각의 흐름

> Rust/Go를 배울지 고민하다 시작했다. 내 스택(C/C++/Java/Python)과 진로(AI/ML 시스템, 특히 DL 컴파일러·저수준 최적화)를 따져보니, 이 분야는 C++/Python이 정답인 곳이고 Rust는 미래 베팅이라는 결론이 났다. 저수준 최적화에 끌리는 이유는 개인적이다 — 아버지가 SK하이닉스 부사장으로 HBM3·HBM3e·HBM4 세계 최초 양산을 이끄셨다. HBM은 곧 이 분야에서 말하는 "memory bandwidth" 그 자체라, 하드웨어와 알고리즘이 만나는 접점에 자연히 관심이 갔다.

흐름은 이렇게 갔다. 언어 고민 → DL 컴파일러라는 목표 분야 확인 → "근데 이 분야 전체 지도를 모른다" → 모델 작성부터 칩 실행까지의 단계 구조를 잡기 → Horace He의 "brrrr" 글이 이 지도의 어디인지 확인 → FlashAttention이 3단계(텐서/루프 최적화)의 대표 사례임을 연결 → 4단계(코드 생성)의 CUDA→PTX→SASS 계단 → 1·2·5단계를 같은 깊이로 채우기 → 마지막에 내가 각 단계를 내 말로 재구성하며 He의 병목 3분류와 매핑.

핵심 질문은 하나였다: **"모델 코딩부터 칩 실행까지 그 사이 과정을 단계로 나눈 게 DL 컴파일러 맞나? 그 큰 그림과 각 단계에 뭐가 있는지를 모르겠다."** 이 노트가 그 답이다.

## 핵심 내용

### 0. 용어 교정 — "그 사이 전부 = DL 컴파일러"는 아니다

모델 작성부터 칩 실행까지 **전체**는 "DL 실행 스택(execution stack)"이다. DL 컴파일러는 그 스택의 **일부**(모델을 받아 최적화된 기계어로 번역하는 구간 = 아래 1~4단계)다. 스택에는 컴파일러 외에 프레임워크(0), 런타임(5), 드라이버·하드웨어(6)가 함께 있다.

비유: "요리 전체 과정"이 스택, "레시피를 주방 동선에 맞게 최적화하는 단계"가 컴파일러. 장보기·불 켜기·실제 가열은 컴파일러가 아니다.

### 단계별 지도 (0~6) — 추상도 높은 곳에서 낮은 곳으로(lowering)

**0단계 — 프레임워크 (컴파일러 아님 / 입력)**
파이썬으로 모델 정의(`nn.Linear`, attention 등). "무엇을 계산할지" 적은 설계도. PyTorch/JAX.

**1단계 — 그래프 캡처 (컴파일러 프론트엔드)**
동적 파이썬 코드 → 정적 **연산 흐름 그래프**로 굳힘.
- 목적은 **overhead 제거**: eager 모드에선 매 연산마다 파이썬 인터프리터·프레임워크 디스패치 비용이 붙는데, 그래프로 통째 굳혀 컴파일하면 그 파이썬 왕복이 사라진다. 핵심은 "파이썬을 실행 경로에서 빼버리는 것".
- compute(FLOPs)는 못 줄인다. 계산량은 그래프로 바꿔도 그대로.
- 핵심 난제 **graph break**: TorchDynamo가 파이썬 바이트코드를 가로채 텐서 연산만 캡처하다, 캡처 못 하는 부분(텐서 값에 따른 파이썬 분기, 미지원 외부 호출)을 만나면 그래프를 끊는다. 끊긴 사이는 느린 파이썬으로 복귀 → graph break를 줄이는 게 성능 관건.
- 캡처 방식 두 가지: trace(예시 입력 흘려 실행된 연산만 기록, 분기 못 잡음) vs 바이트코드 분석(Dynamo, 더 똑똑함. PyTorch 2.0).
- 비유: 즉흥적으로 떠드는 사람 말에서 레시피 문장만 받아적기. 딴소리(제어 흐름) 끼면 받아적기 멈춤(graph break).

**2단계 — 그래프 레벨 IR & 최적화 (컴파일러 중간단)**
1단계 그래프를 **하드웨어 중립적으로** 더 똑똑한 그래프로 다듬음. 다루는 건 "연산들 사이의 관계"(구조), 개별 연산 실행법(3단계)이 아님.
- 연산 융합(fusion) 표시(실제 융합 커널은 3~4단계에서 만듦), 죽은 코드 제거, 상수 접기(constant folding), 대수적 단순화(`x*1`, `x+0`), 메모리 레이아웃 결정(NCHW vs NHWC).
- IR 성격: 여전히 추상적("행렬곱"이 통노드, 내부 루프·메모리 안 보임) = high-level IR. TVM Relay, PyTorch FX.
- 비유: 받아적은 레시피를 보고 "이 두 단계 한 냄비에 합치자(fusion)", "안 쓰는 재료 빼자", "미리 썰자(상수 접기)" — 레시피 자체를 손봄. 주방 동선은 아직 안 정함.

**3단계 — 텐서/루프 레벨 IR & 최적화 (컴파일러 하단) ← 내 관심 정중앙**
"행렬곱 하나"를 실제로 어떻게 돌릴지 결정. 루프 타일링, 데이터를 어느 메모리 계층(HBM↔SRAM↔레지스터)에 어떤 순서로 올릴지, 스레드 분배.
- **HBM과 직결**: "DRAM(HBM)에서 데이터를 언제·얼마씩·어떤 순서로 가져와 빠른 온칩 SRAM에 올릴까"가 이 단계 결정. 성능이 실제로 갈리는 격전지. TVM TIR, MLIR 다이얼렉트.
- **대표 사례 = FlashAttention**: 어텐션의 거대한 N×N score 행렬을 HBM에 안 쓰고, Q·K·V를 블록(타일)으로 쪼개 SRAM 안에서 QKᵀ→softmax→V곱까지 한 번에 처리. FLOPs는 그대로(오히려 약간 늘기도)인데, **HBM↔SRAM 왕복(메모리 트래픽)만 줄여서** 몇 배 빨라짐. 저자(Tri Dao)가 "IO-aware" 알고리즘이라 부름. 이론이라기보단 알고리즘/시스템 엔지니어링(핵심 트릭은 online softmax — 블록으로 쪼개도 정확한 정규화).
- 3단계의 세 기법: 타일링(tiling), 융합(fusion), 재계산(recomputation). FlashAttention은 셋을 어텐션 하나에 다 넣은 종합 결정판.

**4단계 — 코드 생성 / 백엔드 (컴파일러 끝단)**
위 IR → 칩 기계어로 내림(lowering). 계단이 더 있음(CPU와 다른 GPU 특유 구조):
```
CUDA C++  →  PTX  →  SASS(기계어)
```
- CUDA는 4단계 "자체"가 아니라 거쳐가는 **한 형태/입력 언어**. 경로가 꼭 CUDA를 거치는 것도 아님(TVM/XLA는 CUDA 건너뛰고 PTX/LLVM IR로 직행하기도). 사람이 CUDA/Triton으로 손수 짜거나, 컴파일러가 자동 생성.
- **PTX**: NVIDIA의 가상 어셈블리. 진짜 기계어 아님. GPU 세대 바뀌어도 호환되는 이식 가능 저수준 표현.
- **SASS**: 특정 아키텍처(Hopper, Blackwell 등) 종속 **진짜 기계어**. 연산 유닛이 먹는 명령. PTX→SASS는 컴파일 시 미리 or 실행 시 드라이버가 JIT.
- PTX/SASS 두 계단이 있는 이유: GPU는 세대마다 하드웨어가 확 바뀌니 중간 호환 레이어(PTX)를 둬서 코드를 미리 박지 않음.
- CUDA = "그냥 C++ 변형"의 절반만 맞음. C++ + 대규모 병렬 키워드(`__global__`, 스레드/블록 인덱스, `<<<...>>>`). 수천 스레드를 어떻게 쪼개 돌릴지 표현 → 일반 C++와 사고방식 다름.
- **저수준 최적화의 끝**: SASS 레벨에서 "메모리 접근 명령이 HBM 대역폭을 얼마나 효율적으로 쓰는지"가 최종 결정. 위에서 아무리 잘 짜도 SASS가 메모리 명령을 비효율적으로 깔면 HBM을 못 살림.

**5단계 — 런타임 (컴파일러 아님 / 실행 관리자)**
4단계까지의 산출물(커널)을 실제로 GPU에 순서 맞춰 던지고 운영. 컴파일=번역이면 런타임=공연 진행.
- 커널 스케줄링/디스패치: 커널 수백~수천 개를 어떤 순서·스트림에. **비동기 실행**(PyTorch가 GPU보다 앞서 달려 커널을 미리 큐에 쌓음) = overhead를 숨기는 핵심.
- 메모리 관리: HBM 할당/해제. 매번 OS 요청은 느리니 **메모리 풀(caching allocator)** 재활용. "CUDA out of memory"가 이 영역.
- 여러 GPU 분배, 동적 형태(가변 길이) 대응.
- 컴파일러와의 관계: 컴파일러 출력(커널)을 받아 굴리는 **별도 시스템**. ONNX Runtime, TVM runtime, PyTorch 실행 엔진. "정적 번역(컴파일러)" vs "동적 실행 관리(런타임)"의 경계.
- 비유: 다듬어지고(2) 번역된(4) 레시피를 들고 주방에서 불 순서 잡고 냄비 배분하고 요리사 여럿에 일 나누는 주방장. 재료(메모리) 안 떨어지게, 다음 요리 미리 준비(비동기)시켜 주방 안 쉬게.

**6단계 — 드라이버 & 하드웨어 (컴파일러 아님 / 물리·전전공 영역)**
CUDA 드라이버가 커널을 GPU에 올리고, 연산 유닛(Tensor Core)이 계산, HBM↔SRAM↔레지스터로 데이터 실제 흐름. **아버지의 작품이 물리적으로 일하는 층.** 컴파일러 공부 입장에선 "여기부터 하드웨어가 알아서" 처리로 두면 됨.

### DL 컴파일러의 정확한 범위
**1~4단계 = DL 컴파일러.** 0단계는 입력(프레임워크), 5~6단계는 출력을 받아 실행하는 곳(런타임·하드웨어). "그 사이 전부"라는 직관은 거의 맞고, 양 끝은 컴파일러를 둘러싼 스택.

### Horace He의 병목 3분류와 각 단계의 대응 (이 노트의 핵심 매핑)
He의 "brrrr" 글: GPU가 시간 쓰는 곳은 셋뿐 — compute / memory bandwidth / overhead. "지금 어디에 묶였나(bound)"를 진단해야 올바른 최적화를 고른다.

| He의 3영역 | 정체 | 줄이는 주체(단계) |
|---|---|---|
| **overhead** | 파이썬·프레임워크·커널런칭 잡비용 | **1단계**(그래프 캡처로 파이썬 제거) + 5단계(비동기로 숨기기) |
| **memory** | HBM↔SRAM 왕복 | **2~4단계**(fusion, 타일링 — 특히 3단계) |
| **compute** | 실제 FLOPs | 거의 안 줄임. 알고리즘 안 바꾸면 고정 |

He의 글 위치: 컴파일러 "내부 구조(How)"가 아니라 그 앞의 "왜 최적화가 필요한가(Why)" = 진단의 사고 틀. fusion이 왜 이득인지를 하드웨어 1차 원리로 정당화하고, 자동화 한계를 넘는 도구로 Triton을 가리킴. 저자는 PyTorch 팀 소속(AOTAutograd, min-cut 재계산 작업). 입문과 본론 사이의 다리.

## 내 말로 다시 정리

> ⚠️ Claude가 내 발화를 잇대어 만든 초안. 내가 덮어쓸 것.

모델을 파이썬으로 짜고 컴퓨터로 돌리는데, 그 사이 과정을 단계로 나눈 거고 그중 핵심 구간(1~4)을 DL 컴파일러라 부른다.

1단계는 주어진 코드에서 연산을 깔끔하게 처리하려고 연산 흐름 그래프 같은 걸로 가공하는 거다. 이게 최적화되려면 He가 말한 overhead를 줄여야 하고(이름을 compute overhead로 착각했는데, compute랑은 별개 항목이고 그냥 overhead다), 그 방법이 파이썬을 실행 경로에서 빼는 거다.

2단계는 어떤 칩에서 도는지와 상관없이 1단계 결과물을 어떻게 활용하는 게 더 좋을지 한 번 더 최적화하는 거다(그래프 구조를 하드웨어 중립적으로 개선).

3단계가 내 관심 정중앙이다. FlashAttention이 여기 대표 이론(정확히는 알고리즘)이고, 연산은 그대로 두고 HBM↔SRAM 왕복만 줄여서 빨라진 거다. 아버지가 만든 HBM 대역폭을 알뜰히 쓰느냐가 여기서 갈린다.

4단계는 윗단계 코드를 CUDA 같은 커널로 바꾸고, CUDA는 C++ 변형이고(정확히는 C++ + 병렬 키워드), 그다음 기계어로 가는데 한 방이 아니라 CUDA→PTX(가상 어셈블리)→SASS(진짜 기계어) 계단을 거친다.

5단계는 1~4단계 결과물을 실제 돌릴 때 최적화되게 지휘하는 거다. 근데 이건 컴파일러 영역이 아니라 실행하는 주체(런타임)다.

## 잠정 결론

- 모델→칩 전체는 "DL 실행 스택", 그중 1~4단계가 "DL 컴파일러". 관통 개념은 **lowering**(추상도를 한 계단씩 내림).
- 단계 요약: 0 프레임워크(정의) → 1 그래프 캡처(overhead↓, 파이썬 제거) → 2 그래프 IR(구조 최적화, 하드웨어 중립) → 3 텐서/루프 IR(메모리 전략, FlashAttention) → 4 코드 생성(CUDA→PTX→SASS) → 5 런타임(실행 지휘, 컴파일러 아님) → 6 드라이버·하드웨어(물리, 전전공).
- He의 병목 3분류 매핑: overhead=1·5단계, memory=2~4단계(특히 3), compute=거의 고정.
- 내 관심축(HBM·저수준)이 꽂히는 곳: **3단계**(메모리 전략 두뇌) + **4단계 SASS**(메모리 명령) + **6단계**(HBM 물리). 이 셋을 관통하는 게 "대역폭을 살리는가 죽이는가".

## 아직 헷갈리는 것 · 더 파볼 질문

> 학습형 노트. 큰 그림은 잡았으나 각 단계 내부는 의도적으로 안 팠다(이번 목표는 지도였음). 아래는 다음 탐구거리 + 이번에 단정했지만 검증·심화가 필요한 지점.

- **단계 구분(0~6)은 설명용 틀이지 공식 표준이 아니다.** 실제 시스템은 경계가 흐리다. 예: PyTorch Inductor는 2~4단계를 한 덩어리로 처리하고, MLIR은 여러 단계를 한 인프라 안에서 다룬다. 이 7칸을 절대적 분류로 외우면 실제 코드베이스 볼 때 안 맞을 수 있음. (가장 주의할 점.)
- **1단계를 "의사결정 트리"로 비유했던 것**은 부정확. 분기 구조가 아니라 데이터 흐름 그래프(DAG)에 가깝다. 트리/결정트리 이미지는 버릴 것.
- **2단계 fusion "표시"와 3·4단계 fusion "구현"의 경계**가 실제로 어디서 갈리는지 아직 추상적. 어떤 컴파일러는 2단계에서 융합 결정을 하고 어떤 건 3단계에서 한다 — 시스템마다 다른 듯한데 미확인.
- **FlashAttention을 "3단계의 대표"로 깔끔히 분류했지만**, 실제로는 알고리즘 재설계(수학)와 커널 구현(4단계)에 걸쳐 있다. "순수 3단계"로 못 박으면 과단순화. online softmax의 수학, v1→v2→v3 차이(특히 v3의 비동기·저정밀)는 안 팠다.
- **CUDA→PTX→SASS 계단은 NVIDIA 한정.** AMD(ROCm/HIP→GCN/RDNA ISA), 구글 TPU, 기타 NPU는 경로가 다르다. NVIDIA 중심으로만 그림을 그린 것. AscendNPU IR 등 다른 백엔드는 미탐색.
- **"SASS가 HBM 대역폭 효율을 최종 결정한다"는 단정의 강도** 점검 필요. SASS 메모리 명령이 중요한 건 맞지만, 대역폭 효율은 메모리 접근 패턴(coalescing)·캐시·스케줄링 등 여러 층의 합작이라 SASS 단일 귀속은 과할 수 있음.
- **5단계 런타임을 "컴파일러 아님"으로 깔끔히 갈랐지만**, JIT 컴파일·동적 형태 대응처럼 런타임이 컴파일을 실행 중에 수행하는 경우 경계가 흐려진다. "정적 vs 동적"이 항상 깨끗이 안 갈림.
- **다음 탐구 우선순위**: (1) 3단계 타일링이 메모리 계층에 실제로 어떻게 매핑되는지 구체 메커니즘 (2) MLIR Toy Tutorial로 1→4 lowering 직접 구현 (3) `torch.compile`로 간단 모델 IR 덤프해 1~2단계 눈으로 보기 (4) 닭→비행조 비유처럼, NVIDIA 외 백엔드(특히 NPU)에서 이 지도가 어떻게 달라지는가.
